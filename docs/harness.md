# ハーネスの設計図（段階2。下書き）

Blender の拡張機能（レイヤーC）と、推論エンジン（レイヤーA：LLM と Jeff）の間に置く仲介の係（レイヤーB）の設計です。
コードはまだ書きません。ここで決めたことを元に、段階1が終わってから作ります。
考え方は「馬具（導く物）・柵（越えさせない物）・ループ（確かめて戻す）」です。失敗するたびに、同じ失敗が二度と起きないよう環境の側を直します。

## 1. 3つの層

| 層 | 中身 | 動く所 |
|---|---|---|
| A 推論エンジン | LLM（選べる。2章）と Jeff。文や画像を受け取り、答えを返すだけ | それぞれのサーバー（Strata など） |
| B ハーネス | 頼みの受け付け、Jeff での分類、LLM の呼び出し、出力の検証、キャッシュ、ループの管理、記録 | Blender の外の別プロセス（自分の仮想環境） |
| C Blender 拡張機能 | 画面、目録（A8）の道具の実行、測定（A4・A5）、版（A6）、裏の係（A10）、報告（A11） | Blender の中 |

- C は A に直接つながない。B は .blend を直接さわらない。
- B と C の通信は localhost の HTTP。鍵はローカルのトークンファイル（作業フォルダに置き、コミットしない）。
- C は A10 と同じタイマー方式で結果を取りに行く（画面を固めない）。manifest の permissions に network を足し、理由を書く。
- B と C の約束（頼みと答えの JSON スキーマ）は、目録の一覧（`Catalog.listing()`）から作る。目録の指紋（`fingerprint()`）が変われば、B は前置きのキャッシュを作り直す。
- 置き場所は同じリポジトリの `harness/`（目録と約束を共有するため）。拡張機能の zip には入れない。

## 2. LLM の選び方

| 名前 | 動くエンジン | 使い方 |
|---|---|---|
| Qwen3.8 Flash Next | Strata だけ（スペックの関係） | 初めの値。いちばん性能が高い |
| Gemma 26B | Strata か、ほかのローカルのエンジン | 予備 |
| Gemma 31B | Strata か、ほかのローカルのエンジン | 予備 |

- 拡張機能の設定で選ぶ。ハーネスは「エンジンの係（adapter）」を1つずつ持ち、エンジンごとの違いをそこに閉じ込める。
- adapter は、できることの印を持つ：JSON スキーマで出力を縛れるか、アシスタントのプリフィル、思考の切り替え、前置きのキャッシュ、画像の入力、1秒のトークン数（Mac mini で測る）。
- できないことがあるエンジンでは、ハーネスが代わりをする（スキーマで縛れなければ、出たあとに厳しく検証してやり直す。回数に上限）。
- 記録（A15）に、どのエンジン・どのモデル・どの量子化で答えたかを残す。

## 3. 1回の頼みの流れ

```
C：日本語の頼み＋選んだファイル＋モデルの要約カード（C3）の指紋 を B に送る
B：プログラムの確かめ（ファイルがあるか、作業フォルダの中か、形式は FBX・OBJ か）
   → だめなら、LLM も Jeff も呼ばずに、すぐ理由を返す
B：Jeff に分類させる（プログラムが作る決まった英語の文）
   → 目録の分類のどれか、または「目録に無い」
   → 「目録に無い」なら LLM を呼ばずに断る。自信が低ければ LLM に回す
B：LLM に、その分類の道具（5〜10個）だけを見せ、道具と値を JSON で選ばせる
   （思考を飛ばすプリフィル、スキーマで縛った出力、変わらない前置きはキャッシュ）
B：答えを目録のスキーマで検証し、値を範囲に丸める → C に「計画」として返す
C：計画を見せる → 確認（変更は計画の承認、消す操作は毎回）→ 写しで実行 → 測る → 報告
B：測った結果を受け取り、ループ（5章）に進むか決める
```

## 4. 馬具（導く物）

- プロンプトはプログラムが決まった形で作る。変わらない部分（決まりの文、分類の道具の一覧、モデルの要約カード、シェイプキーと材質の一覧）を先に、変わる部分（頼み、いまの値の差分）を最後に置く。前置きはキャッシュに乗せ、毎回は差分だけを送る。
- キャッシュが消えたとき（エンジンの再起動など）でも、同じ前置きを作り直せるようにする。キャッシュの鍵は「決まりの文の版・目録の指紋・カードの指紋」。
- 思考は飛ばし、1トークン目から JSON にする（10 トークン/秒のため）。出力は「道具の id と値」だけの短い形にする。
- 難しい選択は分けて小さくする：Jeff が分類 → LLM が道具と値。数字の計算はプログラム。
- 値は、意味の名前（例：胸の大きさ、腰の細さ、肌のツヤ）で選ばせる。モデルの本当のシェイプキーや材質の入力への対応は、辞書と登録カードで決める（A3 の骨の辞書と同じ形。辞書に無い物だけユーザーに聞く）。これでどのモデルでも同じ言葉で頼める。

## 5. 柵とループ

柵（越えさせない物）：

- 動くのは目録の道具だけ。返事をコードや式として動かさない。断るかどうかは、目録に道具が無いことで決まる。
- 値はスキーマの最小と最大の中だけ。プログラムが丸める。
- 形を変える道具は、必ず写しで試し、前後の数字と画像を見せてから。元のファイルは上書きしない。
- アプリの Model フォルダには書かない（書き出しは作業フォルダへ）。
- 時間切れ、中止、ループの回数、トークンの量に上限。

ループ（確かめて戻す）：

- 写しに当てる → 測る（めり込みの深さ、62方向のカメラから見える点、伸び、体積）→ 判定 → 上限つきで直す → ユーザーの確認 → 版で保存。
- 判定はプログラムの基準が先。灰（測れなかった物）を Jeff や LLM に決めさせない。
- 画像（複数の向きの撮影）を LLM に描写させるのは補助（ロードマップ C9）。画像の判定は「黄（気をつける）」を足すだけで、赤を緑にはできない。
- 失敗した例は「見本」として記録し、自己テストと頼みごと集（C4）に足す。

## 6. Jeff の受け持ち

- 頼みの分類（どの分類の道具を使うか、または目録に無いか）。
- 言葉の選択：ユーザーの言葉がどの服のファイルを指すか（候補はプログラムが作ったファイルの一覧）、服の種類、どの直し方を先に試すか。
- 入力は、プログラムが作る決まった英語の文だけ。選択肢の名前は数字だけにしない。
- 自信が低ければ LLM に回し、それでも決まらなければ2〜3個の候補のボタンでユーザーに聞く。
- ファイルがあるかどうか、測った数字の良し悪しは、Jeff に聞かない（プログラムが決める）。

## 7. 新しく足す道具（計画に入れる。番号は決めるときに付ける）

- 服の自動フィッティング：取り込み（FBX・OBJ）、体の目印に合わせた大きさと位置、Surface Deform・Shrinkwrap、Data Transfer のウェイト（B4）、関節のなめらかさ、隠れた体の MASK（convert_blend.py が焼き込む形）。
- 体型と解剖学的ディテール：シェイプキーの値と、材質（ノーマル・色のブレンド率）の連動。揺れ物の物理の値の再計算。大人の体のモデルに使う前提。
- 頭身・プロポーション：骨のスケールの比。アプリには休みの姿勢で書き出されるので、休みの形に焼き込む手順が要る。
- 表情の合成：基本のキーを混ぜて新しいキーを作る。アプリで使うには Expr_* の決まりに合わせる。

アプリに出したい物は、convert_blend.py が何を焼き込み、何を落とすか（CLAUDE.md 4章）に合わせて作る。

## 8. 試し方

- ふつうのテストは、記録した返事で動く「練習用の相手」で回す（クラウドでも動く）。
- 本物のエンジン（Strata・Jeff）を使う試しは別に分け、Mac mini で行う。
- 頼みごと集 約300件で、道具の選び方 95% 以上、値が範囲に入る 90% 以上、確認なしの変更 0、Jeff の自信と正解率のずれ 5% 以内（ロードマップ段階2のまま）。
- エンジンごと（Flash Next・Gemma 26B・31B）に同じ頼みごと集で採点し、速さと正解率を並べて記録する。

## 9. まだ決まっていないこと

- Strata の API の形（OpenAI 互換か）、スキーマで縛れるか、プリフィルとキャッシュの効き方、画像を受け取れるか。
- Jeff の API と、日本語を受け取れるか（いまは英語だけの前提）。
- 服は同じ素体用の物だけか、ほかのモデルの服も着せるか。
- 体型・材質・頭身・表情の変更を、アプリにも出すか（出すなら焼き込みの手順が要る）。
